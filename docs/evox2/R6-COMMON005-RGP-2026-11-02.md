## Minimal opt-in host cue

The env var `LLAMA_EVOX2_RGP_SSE_TRACE=1` makes the CLI SSE receiver emit flushed stderr lines of the form:

```text
evox2_rgp_sse_v1 event=request_start elapsed_ms=0 text_deltas=0
evox2_rgp_sse_v1 event=first_text_delta elapsed_ms=... text_deltas=1
evox2_rgp_sse_v1 event=text_progress elapsed_ms=... text_deltas=32
evox2_rgp_sse_v1 event=text_progress elapsed_ms=... text_deltas=64
evox2_rgp_sse_v1 event=stream_end elapsed_ms=... text_deltas=...
```

Only **nonempty reasoning/content SSE delta messages** count. `text_deltas` is **NOT token count**, `elapsed_ms` is a **client-local monotonic duration**, and arrival of `first_text_delta` is **after** the server generated its first text. Logs are **not GPU-timestamp markers** and do not identify the selected kernel or layer. The SSE client may lag GPU work; use the RGP event timeline itself for timings and do not align these times as exact dispatch boundaries.

With the flag unset, set to 0, or any value except literal `1`, no marker lines are emitted. This experiment adds no RGP dependencies to the backend and should leave normal inference unchanged. The `LLAMA_` prefix is included by the existing benchmark environment recorder.

## Narrow diagnostic run / capture workflow

1. Open Radeon Developer Panel and configure **ROCm/HIP** GPU capture for `llama-cli` / its spawned `llama-server` inference process (confirm which executable actually owns GPU dispatches). RGP/RDP settings differ by version; verify a process association and a GPU kernel timeline rather than assuming the CLI host messages are GPU events. Start with **Auto Capture disabled** and a short manually triggered dispatch/timing capture.
2. Dry run the one-job plan:

```powershell
.\tools\evox2\benchmark\Invoke-BenchmarkMatrix.ps1 `
    -Plan .\tools\evox2\benchmark\configs\qwen38-r6-rocm-qsa-rgp-128k-20261102.psd1 `
    -PlanOnly
```

3. Execute a single 128k MTP-OFF diagnostic run (no batch matrix or additional 256k run):

```powershell
.\tools\evox2\benchmark\Invoke-BenchmarkMatrix.ps1 `
    -Plan .\tools\evox2\benchmark\configs\qwen38-r6-rocm-qsa-rgp-128k-20261102.psd1 `
    -OnlyJob rocm-qsa-rgp-tg -OnlyCase 128k -OnlyVariant mtp-off-trace -StopOnError
```

4. Wait until **first generated text is visible** (or `first_text_delta` in a live console/log). Trigger the RDP capture **during ongoing generation**, preferably after initial output stabilizes (e.g. around the 32nd nonempty text delta), avoiding PP, model loading and process teardown. If automatic capture must be used, calibrate the dispatch window first; never assume the Vulkan r5 dispatch ordinal mapping applies to HIP.
5. In RGP, inspect per-dispatch kernel names and durations, especially `flash_attn_tile`, `k_get_rows`, `lightning_indexer`, top-k, mask/set-rows, memory transfers, and large matmul. Confirm which events truly are QSA, not full-attention layers, via frequency/shape and source. Old r3 per-layer 128k reference is **flash_attn_tile ~1.452 ms, k_get_rows_float ~0.451 ms**, with caveats about source changes; these are historical comparison cues, not expected matching times.
6. Save the RGP capture outside the repository. Send the `.rgp` (if practical), RGP Events/Event Timing screenshots/CSV, and the **benchmark ZIP** with `result.json`, `conditions.json`, `output.log`/`stderr.log`. Verify `evox2_rgp_sse_v1`, `Status=OK`, GPU model, P-MODE, process/binary identities, actual prompt and output counts. Some wrappers write multiplexed stderr in `output.log`, so inspect both.
7. If first capture misses TG or cannot be associated with the real HIP process, **stop and review capture settings**. Only after a valid 128k RGP trace decide whether 256k is needed. No automatic long repeated tests.

**Safety:** Never run the broad ROCm `FLASH_ATTN_EXT` backend suite or `Build-ROCm.ps1 -RunBackendTest` on Windows gfx1151 (prior WATCHDOG/Kernel-Power). Instrumentation is diagnostic, not a performance baseline. If compiled opt-in mode fails, keep/use the original frozen b11908 and report the failure.
