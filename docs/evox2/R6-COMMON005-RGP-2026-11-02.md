## Minimal opt-in host cue

The env var `LLAMA_EVOX2_RGP_SSE_TRACE=1` makes the CLI SSE receiver emit flushed stderr lines of the form:

```text
evox2_rgp_sse_v1 event=request_start elapsed_ms=0 text_deltas=0
evox2_rgp_sse_v1 event=first_text_delta elapsed_ms=... text_deltas=1
evox2_rgp_sse_v1 event=text_progress elapsed_ms=... text_deltas=32
evox2_rgp_sse_v1 event=text_progress elapsed_ms=... text_deltas=64
evox2_rgp_sse_v1 event=stream_end elapsed_ms=... text_deltas=...
```

Only **nonempty reasoning/content SSE delta messages** count. `text_deltas` is **NOT token count**, `elapsed_ms` is a **client-local monotonic duration**, and arrival of `first_text_delta` is **after** the server generated its first text. Logs are **not GPU-timestamp markers** and do not identify the selected kernel or layer. The SSE client may lag GPU work; use the RGP event timeline itself for timings and do not align these times as exact dispatch boundaries.

With the flag unset, set to 0, or any value except literal `1`, no marker lines are emitted. This experiment adds no RGP dependencies to the backend and should leave normal inference unchanged. The `LLAMA_` prefix is included by the existing benchmark environment recorder.

### What was observed

- Capture A, event 531: `flash_attn_tile<256,256,1,4,false>` **1,490.759 us**, `k_get_rows_float` event 501 **405.008 us**, `lightning_indexer_kernel_vec` event 505 **124.728 us**, `top_k_mask_kernel` event 529 **8.420 us**. The wavefront occupancy panel reports for the FA event VGPR 239, LDS 19456 bytes, occupancy 6/16. One representative FA event is not sufficient to infer a precise kernel-wide bottleneck.
- Capture B: several `flash_attn_tile<256,256,1,4,false>` launches **~1.467–1.488 ms**, `k_get_rows_float` **~0.404–0.406 ms**, one `mul_mat_vec_q<type14>` **2,846.123 us**, while smaller `top_k_mask_kernel` entries remain around **8 us**. The 2.846 ms matvec is consistent in scale with the historical r3 128k **~2.835 ms**. This is **not** evidence of a rare regression without repeated per-kernel statistics.
- Capture A barriers: **1.13%** of reported frame, 2,048 cache invalidations, zero flushes. Capture B: **0.69%**, 2,158 invalidations, 22 flushes. RGP lists some barrier `Duration` values around 1.49 ms matching the preceding FA runtime, but `Drain Time` on these rows is ~0.1–0.2 us. **Do not add full Duration to kernel time or claim a 1.49 ms barrier stall.**
- The `Most expensive events` panel reports the highest 5% of events accounting for about **76%** of profile GPU time in A and **80%** in B; the visible names include FA, get-rows, matvec and gated-delta-net. The display is per-event, not a grouped kernel-total ranking.
- B's wavefront occupancy overview shows a conspicuous low-activity gap after a large compute block before work resumes. Its origin is **unproven**: possibly CPU/queue scheduling, capture overhead, or token boundary; avoid attributing this to COMMON-005 until an event/queue correlation shows the cause.
- Comparison to r3 RGP: r3 128k `flash_attn_tile` ~1.452 ms and `k_get_rows_float` ~0.451 ms. The retained long-KV attention path in r6 is **strongly supported**. Do not imply the modern `k_get_rows_float` is necessarily the same old full-cell score expansion: modern `build_qsa_sel` uses pooled-key gathers and `pool_idxs`/top-k. Identify its precise node before predicting it disappears with the new Gather.
