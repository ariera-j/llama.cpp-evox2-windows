## 配置と実行経路

1. `src/models/qwen4exp.cpp` は16個の分割 PLE head を個別のレイヤー番号付き重みとして作る。`src/llama-arch.cpp` の `LLM_TENSOR_PLE_NGRAM_EMBD` は repeating layer の `GGML_OP_GET_ROWS`。`src/llama-model.cpp` は指定された GPU レイヤーのバッファ候補を GPU 優先で並べる。
2. `src/llama-model-loader.cpp` の `select_weight_buft` は、候補ごとに `weight_buft_supported` で重みと長さ512の I32 インデックスから代表 GET_ROWS を作り、対応判定を通過した最初の候補を選ぶ。変更前は幅160が `160 % 256 != 0` で拒否され、ROCm バッファを選べなかった。既存の `get_rows_cuda_kq` も同じ256要素の整列を要求し、行幅を256で割った個数だけ処理する。
3. 変更後、`ggml-cuda.cu` の IQ4_NL 判定は、正の32要素倍数、ブロックとインデックスの要素幅・アラインメント、I32 の正の有効な取得次元、入力バッチと出力形状の一致、連続 F32 出力を要求する。`ggml_get_rows` が IQ4_NL から生成する出力は連続 F32。ソースの行・バッチ stride はバイト単位のまま使い、アラインメントを満たす view を許容する。I32 のインデックス stride は要素数へ変換する。インデックス値は呼び出し側が `0 <= id < src->ne[1]` を満たす既存の契約。
4. 実行時、モデルは head ごとに I32 の行インデックスを1次元 view として渡し、結果を列方向に連結する。`ggml_cuda_compute_forward` から `ggml_cuda_op_get_rows`、`get_rows_cuda` を経て F32 の型 dispatch に入る。`getrows.cu` は `ne00 % QK_K == 0` なら従来の32スレッド・256要素経路を使用する。それ以外の32要素倍数では同じカーネルのテンプレートを4スレッド・32要素で起動する。他の量子化型は従来のテンプレート既定値と対応判定を使う。
5. `dequantize.cuh` で既存の IQ4_NL デコードを1ブロックの関数に切り出した。IQ4_NL のブロックは先頭に FP16 scale 2 byte、その後に16 byteの packed nibble を持つ。スレッド `t=0..3` は byte `4*t+j`（`j=0..3`）の low/high nibble を同じ `kvalues_iq4nl` で引き、各値を FP32 の scale で乗算して列 `4*t+j` / `4*t+j+16` に書く。256経路では従来どおり `tid%8` が32要素ブロック、`tid/8` がブロック内の担当。CPU 参照は `ggml_compute_forward_get_rows_q` から型特性の `dequantize_row_iq4_nl` に到達し、同じ packing と codebook を使う。

`grid.x` は取得行、`grid.y` は行内のデコード単位、`grid.z` はバッチ。幅160では1行90 byteからオフセット0、18、36、54、72の5ブロックを読み、出力列0–159を各1回書く。行の開始は `id*nb01+i11*nb02+i12*nb03`、出力の開始はバイト換算で `i10*nb1+i11*nb2+i12*nb3`。y/z は65,535で上限を取り、それぞれの grid 次元を刻み幅として反復する。バッチ座標 `(i11,i12)` は `z / ne12, z % ne12` で全組を列挙する。対応判定は `ne11*ne12 <= INT32_MAX` として fast division の加算の桁あふれを防ぎ、起動時の `grid.x * block.x < 2^32` も満たす。CUDA/HIPで同じ型とデコーダを使うため共有実装とした。 [HIP の起動制限](https://rocm.docs.amd.com/projects/HIP/en/develop/reference/hip_runtime_api/modules/launch_api.html)

GGUF メタデータどおりの幅160・連続行と、対象レイヤーに ROCm デバイスのバッファが提示される設定なら、代表 GET_ROWS と実グラフの head ごとの GET_ROWS はどちらも新しい判定を通る。対象デバイス固有の通常バッファは `supports_buft` の条件を満たす。レイヤーの offload 設定、明示的なテンソル配置 override、実際の GPU メモリ確保は別途実機で確認が必要。分割 PLE 側の loader とモデル定義の変更は不要と静的に判断した。 [既存の16 head とメモリ予算の調査](https://github.com/ariera-j/llama.cpp-evox2-windows/blob/891e2605fbc0798228ffad2a69dd618f6cdab216/docs/evox2/ROCMFP4-HIP-PORT-REVIEW-2026-11-26.md)

## テストケース

`tests/test-backend-ops.cpp` の既存 `test_case` と CPU グラフ比較を利用する。全件のインデックスの基本列は `I=[4,0,2,4,1]`。先頭・末尾・中間と重複・非昇順の複数行を含む。padded のバッチでは `I` を `i11+2*i12` 個だけ左回転する。表の stride と view offset は byte 単位。

| 幅 / padded | IQ4_NL 入力形状 | 入力 stride `nb[0..3]` / offset | I32 形状、stride `nb[0..2]` / offset、値 | 出力 | 期待する経路と結果 |
| --- | --- | --- | --- | --- | --- |
| 32 / 0 | `[32,5,1,1]` | `[18,18,90,90] / 0` | `[5,1,1]`、`[4,20,20] / 0`、I | 連続 F32 `[32,5,1,1]` | 32経路、1ブロックと全行がCPU一致 |
| 160 / 0 | `[160,5,1,1]` | `[18,90,450,450] / 0` | `[5,1,1]`、`[4,20,20] / 0`、I | 連続 F32 `[160,5,1,1]` | 32経路、5ブロックと全行がCPU一致 |
| 160 / 1 | `[160,5,2,3]`、親 `[224,7,2,3]` | `[18,126,882,1764] / 144` | `[5,2,3]`、`[4,28,56] / 4`、バッチごとに回転 | 連続 F32 `[160,5,2,3]` | 32経路、両入力の view offset・行と2バッチ次元の stride を含めCPU一致 |
| 256 / 0 | `[256,5,1,1]` | `[18,144,720,720] / 0` | `[5,1,1]`、`[4,20,20] / 0`、I | 連続 F32 `[256,5,1,1]` | 既存256経路、8ブロックと全行がCPU一致 |
| 288 / 0 | `[288,5,1,1]` | `[18,162,810,810] / 0` | `[5,1,1]`、`[4,20,20] / 0`、I | 連続 F32 `[288,5,1,1]` | 32経路、256境界を超えた9番目を含めCPU一致 |

`std::mt19937` の seed は `0x504c4531`。整数化したサンプルから有限の F32 を生成し、既存の CPU 量子化で入力を用意する。行・ブロックで値が変化するため、5ブロック目や行・バッチ境界の読み違いは CPU 参照と比較できる。出力は NaN で初期化し、書き残しは既存の NaN 検査で検出する。既存の Inf 検査と既定 NMSE `1e-7` を適用する。幅の拒否はメタデータの条件を静的に確認し、不正な量子化テンソルを構築するケースは登録しなかった。

## D0-2 の計画

下記は運用者がソースレビューと限定 GPU 数値検証を個別承認した後の1回分。2026-11-26 の Adrenalin 更新後も、既知の backend-op 障害の解消は未確認。先に別途承認済みの方法で `w55\build-rm` に新規ビルドし、ソース SHA、EXE ハッシュ、CMake の HIP/gfx1151 設定、TheRock の DLL/データとマニフェストを照合する。以下のファイルパスはその承認後ビルドの予定先。既存 b12696 の EXE にはこの変更とテスト登録が入っていない。 [標準ビルドの出力構成](https://github.com/ariera-j/llama.cpp-evox2-windows/blob/891e2605fbc0798228ffad2a69dd618f6cdab216/docs/evox2/automation/BUILD-VALIDATION-20261126.md)

```powershell
& 'C:\llama-build\automation\w55\build-rm\bin\Release\test-backend-ops.exe' test -b ROCm0 -j 1 -o GET_ROWS -p '^type=iq4_nl,d0_1_width=(32,padded=0|160,padded=[01]|256,padded=0|288,padded=0)$'
```

- `main` は `-b` をデバイス名の完全一致として扱い、他のデバイスではテストを起動しない。HIP ビルドの接頭辞は `ROCm`、デバイス名は接頭辞と列挙番号から成る。同じビルドの検証済みデバイス列挙で `ROCm0` が Radeon 8060S（gfx1151）であることを確認する。CPU backend は参照として初期化され、利用可能な `ggml_backend_cpu_set_use_ref` が有効になる。`ggml_backend_load_all` による登録とデバイス列挙は先行する。
- `make_test_cases` の `-p` は `vars()` に対する `std::regex_search`。両端アンカー付きの式は上表の登録5件だけに一致し、`-o GET_ROWS` も演算名の完全一致で照合する。ケース一覧の CPU 側生成は行うが、対象外の演算グラフへの GPU 割り当て・計算は行われない。`run_fa_vec_slice` も `-o` が `FLASH_ATTN_EXT` を選ばないため即時 return する。各ケースの演算グラフは GET_ROWS とその入力・view、既存テストの sentinel のみ。`-j 1` で1ワーカー。想定は ROCm 上の GET_ROWS 5件と各件の CPU 参照比較。
- PASS は Radeon 8060S の確認、5件すべての個別 `OK` と `5/5 tests passed`、終了コード0、監視・回復・イベント条件の通過をすべて満たした場合。既存ハーネスでは非対応が分母に含まれず一部スキップでも終了0となり得る。件数不足、対象外の出力、非対応、差分、NaN/Inf、GPU エラー、非ゼロ終了は失敗扱い。

### 起動と監視手順

1. 運用者が Windows PowerShell 5.1 で単発起動を監督する。作業ログ用の一意の実行 ID を採番し、`C:\llama-build\_logs\codex` に実行引数、バイナリと SHA-256、開始 UTC、stdout/stderr の分割ログを作る。実行中の推論・ビルド・バックエンドテスト・モニターと Task Manager の不在を確認する。P-MODE は固定 main の承認済み `Get-Evox2PModeMetadata` で Performance を確認する。
2. 起動前に固定 main の `Evox2.Memory.psm1` の `Get-Evox2SystemMemory` で物理空き・commit・commit limit を採取する。WDDM は `Get-Counter` の `\GPU Adapter Memory(*)\Dedicated Usage` と `\GPU Adapter Memory(*)\Shared Usage`、GPU 利用率は `\GPU Engine(*)\Utilization Percentage` を読み取り、時刻と有効なサンプルを保存する。観測値を取得できない場合は開始を保留する。既存ゲートどおり物理空き16 GiB以上を要求し、終了後は同じ測定で物理空き16 GiB以上、開始時比で commit と WDDM Dedicated の増加がそれぞれ4 GiB以内、P-MODE が Performance、対象と監視 PID が終了したことを確認する。
3. 開始前に `Get-WinEvent -LogName System -MaxEvents 1` と `Get-WinEvent -LogName Application -MaxEvents 1` で EventRecordID を控える。終了後は両チャネルのカーソルを再取得し、`Get-WinEvent -LogName <channel> -FilterXPath '*[System[EventRecordID > <before-id>]]'` で新規イベントを保存する。Display/GPU・WHEA・BugCheck・リソース枯渇・Application Error/Hang・WER を確認し、WER は障害の発生時刻も照合する。Kernel-General 12 の最終起動時刻が前後で一致することも確認する。正常な `NoMatchingEventsFound` は0件とし、アクセス拒否・カーソル巻き戻り・読取りエラーは監査失敗とする。
4. 監督用の同一シェルから、上記の EXE と引数を `Start-Process -PassThru` と `-RedirectStandardOutput` / `-RedirectStandardError` で1回だけ作成する。子の `Id` と `StartTime` を保存し、`Stopwatch` と `WaitForExit(2000)` で2秒間隔の確認を行う。必要な RAM・commit・GPU の観測値と PID の WorkingSet/PrivateBytes を記録する。提案の実行上限は起動から **60秒**。タイムアウト・重大異常時は PID と開始時刻が一致する子だけを停止し、終了と残留を確認する。SSH 切断時は次のコマンドを送らず、監督シェルの結果・PID・実機の応答を運用者が照合する。
5. 異常終了、GPU エラー、応答停止、SSH 切断、重大イベント、回復不良、監視欠損のいずれかで停止する。部分ログ、PID と開始時刻、取得済み監視値、前後のイベント境界と新規イベントを同じ実行 ID で保全し、運用者へ渡す。再試行は運用者の判断を待つ。 [ランブックの停止手順](https://github.com/ariera-j/llama.cpp-evox2-windows/blob/891e2605fbc0798228ffad2a69dd618f6cdab216/docs/evox2/automation/RUNBOOK.md#無人計測の-run-単位の停止手順) · [イベントログ読み取り](https://github.com/ariera-j/llama.cpp-evox2-windows/blob/891e2605fbc0798228ffad2a69dd618f6cdab216/docs/evox2/automation/EVOX2-ENVIRONMENT.md#ssh-のイベントログ読み取り)

## 静的検証とレビュー事項

- GPU を使わない Python のアドレス列挙で5件の全8,480出力位置を確認した。各出力に対し入力バイト・nibble と出力位置が CPU の行選択式と一致し、欠落、重複、バッファ境界外がなかった。y/z の65,535境界の反復、fast division の境界値、256経路の32スレッドのデコード配置、HIP の x 次元上限、ケースフィルターの5件一致も確認した。
- 幅・型・stride・取得次元と dispatch の条件を突合した。既存256経路のデコード式と起動形状、IQ4_NL 以外のサポート分岐とテンプレート引数、CPU・Vulkan・loader・モデルコード・共通ツールへの影響範囲を差分で確認した。`git diff --check` は通過した。
- レビューでは、非整列経路の4スレッド workgroup、batch 上限とアラインメント判定、padded view の CPU 比較、`5/5` と実機監視を両方要求する D0-2 の判定を確認する。小さな workgroup を使う新経路の実モデル性能と GPU メモリの回復は未確認。CPU 配置が減った場合の物理空き・commit・転送量も後続の実測事項。
- D0-1 の確認範囲はソース・テストの静的検証まで。configure、ビルド、`test-backend-ops.exe` の起動、HIP/CUDA の GPU 数値比較、モデルロード・配置確認・推論、性能計測はいずれも未実施。
