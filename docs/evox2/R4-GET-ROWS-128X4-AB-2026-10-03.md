# r4 Vulkan GET_ROWS 128x4: source review, A/B plan and results

Status: 2026-10-03 JST, small cached-gather gate closed after the Windows 64k
profile OFF/ON pair. No steady cached-gather or GPU-total improvement was
observed. Keep the candidate default OFF, skip normal ABBA and 128k/256k tests
for this candidate, and proceed to VULKAN-002. Dedicated GPU correctness logs
were not included in the supplied profile archive; no numerical pass is claimed.

## Purpose and source checkpoint

Base: `r4/upstream-refresh-20261002`,
`43feb2263fe30720881e2d020a116275375c1e37` after COMMON-001 validation.

The preserved pre-COMMON-001 Original 64k / MTP OFF / legacy-MoE profile reports:

| Steady GPU operator timing | ms/token |
|---|---:|
| GET_ROWS total | 2.48727 |
| cached pooled-key gather | 1.66209 |
| raw-key update gather | 0.03014 |
| all GPU operators | 40.671 |

Cached gather is 66.82% of GET_ROWS and about 4.09% of the GPU operator total.
These are profiler timings, not normal inference wall-clock time or a promised
TG gain. The QSA input/selection source matches the profile checkpoint
`acf7fea2b`; COMMON-001 did not change this part of the graph.

The cached gather reads `128 x 15488` f16 pooled keys from interleaved
raw-key/pooled-key KV storage and produces contiguous f32 rows for pool scoring.
Its output size is 7.5625 MiB/layer, 90.75 MiB across 12 QSA layers per token;
these logical tensor sizes are not measured physical DRAM traffic.

r3 COMMON-004 used a dedicated contiguous f32 pool buffer and read it by view.
r4 instead stores each completed pool in its last member cell and gathers by
`pool_cells`. General view replacement would need to handle variable cell ids,
repeated dummy padding ids and graph reuse. Current score reshapes require
contiguous tensors; the four-query Vulkan matvec path also copies non-contiguous
inputs. A separate persistent compact buffer would require allocation,
invalidation, sequence/state and fallback management. That is outside this gate.

## Initial source review (before implementation)

Reviewed r4 `43feb2263fe30720881e2d020a116275375c1e37` against frozen r3
`0a93fcbb8e5bcf51b331275c4f4b142d822168d6` / COMMON-004.

- `src/models/qwen4exp.cpp`, `build_qsa_sel()`: the cache path writes updated
  pools, then calls `kpool_cache.gather_pooled(inp_kpool->pool_cells)` for scoring.
- `src/llama-memory-hybrid-idx.cpp`, `gather_pooled()`: this is
  `ggml_get_rows(ctx, pooled, idxs)`. The pooled view is the second half of each
  indexer-KV cell, whose layout is raw key followed by pooled key. Each completed
  pool is stored in its last member cell.
- In ordinary single-sequence decode a new four-token pool completes once every
  four tokens, but the saved pool gather runs every token in all 12 QSA layers.
  Update inputs are padded to at least one pool for stable graph shapes. The
  cost is copying cached f16 keys into contiguous f32 scoring rows, rather than
  repeating pooled-key norm/RoPE calculation.

| Property | r3 COMMON-004 | r4 reviewed cache path |
|---|---|---|
| Storage | Dedicated contiguous f32 pooled buffer | Pooled half of indexer-KV cells; f16 in this test |
| Scoring input | Direct buffer view after updates | GET_ROWS using variable `pool_cells` |
| Management scope | Restricted single-sequence path | Streams, shared cells and sequence editing |

The initial alternatives and decision were:

| Alternative | Assessment |
|---|---|
| Replace gather directly with a view | Not general: cell representatives can vary and padding repeats a dummy cell |
| Conditional strided view | Requires layout checks and reshape changes; current four-query Vulkan matvec also copies non-contiguous inputs |
| Dedicated compact pool buffer | Needs allocation, invalidation, state/sequence handling and fallbacks; outside this small patch |
| Skip gather on tokens without pool updates | Needs a persistent expanded destination and invalidation; not a local graph-node deletion |
| Improve GET_ROWS workgroup layout | Selected for one opt-in A/B without changing cache/graph semantics |

The non-contiguous-input copy is in the Vulkan matvec preparation path in
`ggml/src/ggml-vulkan/ggml-vulkan.cpp`. Removing the GET_ROWS node alone would
therefore not establish that copying was eliminated. The chosen hypothesis was
that the generic 512-column workgroup wastes 384 invocations for a 128-column
row; packing four rows might reduce scheduling cost. This was a source-level
hypothesis, not a measured bottleneck attribution or speedup promise.

## Implemented candidate

Environment control, sampled when the Vulkan device is created:

```text
GGML_VK_GET_ROWS_128X4=0  -> existing route
GGML_VK_GET_ROWS_128X4=1  -> opt-in route for eligible shapes
```

Unset, `0`, empty and all other values retain the existing route. Use separate
child processes for A/B; changing the variable after device creation is not an
in-process toggle. Startup logs explicitly report `GET_ROWS 128x4 = on/off`.

Eligibility is based on tensor metadata, not names or qwen-specific addresses:

- source f16, destination f32, source width exactly 128;
- contiguous elements within a source row (`nb[0] == 2`);
- one-dimensional i32 ids with `nb[0] == 4` and at least 256 selected rows;
- contiguous destination.

Arbitrary valid source row strides and source/ids view offsets remain supported.
Small decode raw updates (four selected rows here), other widths/types, f16
destinations and batched ids retain the original route. Eligible PP gathers can
also use the candidate, so PP is measured rather than assumed unchanged.

The new `get_rows_f16_f32_128x4` shader variant uses 128 columns x 4 rows per
workgroup and the matching dispatch divisors `{128,4,1}`. It reuses the existing
shader body, ids, stride/offset handling, grid-limit loops and f16-to-f32
conversion. Generic variants retain `{512,1,1}`. The graph, cache layout,
pool-domain selection, attention and fusion rules are not changed.

For the measured 15488-row gather, the workgroup count is 15488 -> 3872 per
layer. The original 512-thread workgroup has only 128 data-processing invocations
for this width; packing four rows uses the existing 512-thread budget fully.
This does not imply a fourfold speedup. The 256-row gate is a conservative
experiment boundary, not a measured hardware optimum; do not start a threshold
sweep before the primary A/B result.

## Validation completed in the implementation environment

- `vulkan-shaders-gen.cpp` compiled with g++ C++17.
- The complete modified `test-backend-ops.cpp` passed C++17 syntax checking
  against the pinned ggml headers.
- Default F16/F32/BF16/I32 shader variants preprocess to the same code as the
  baseline; only the new variant expands its workgroup declaration to 128x4.
- The actual selector predicate was extracted, compiled with the real ggml
  tensor definitions, and checked for eligible/fallback metadata.
- The actual GET_ROWS shader body was executed in a host C++ harness for both
  workgroup layouts. Sixteen cases checked exact finite f16-to-f32 values,
  every output written exactly once, intact output guards, interleaved and
  contiguous sources, view offsets, duplicate ids, partial tiles and capped
  dispatch loops. Rows included 4, 255, 256, 257, 15488, 15491 and 70003.
- `git diff --check` passed.

These checks are not SPIR-V compilation, full Vulkan backend compilation or GPU
execution. The environment does not have glslc/PowerShell/a usable Vulkan GPU.
Windows build and the real backend tests below are required before profiling.

## Decision and stop rule

| Result | Next action |
|---|---|
| Value/build failure | Fix the local dispatch bug or abandon the candidate; no speed claims |
| Cached gather improves and GPU total improves | Run normal ABBA |
| Normal improvement is clear against run spread, PP acceptable | Keep opt-in and validate 128k/256k in a separate follow-up |
| Gain is negligible, inconsistent, or offset by a regression | Record the result, leave default OFF and advance to VULKAN-002 |
| Benefit needs cache layout changes or gather/matmul fusion | Stop this gate and advance to VULKAN-002 |

Do not implement long-context tuning, dedicated pool buffers or a threshold
sweep in this patch. The first decision uses these two profile runs and four
normal runs; add repetitions only to resolve an actual ambiguous result.

### Decision (user accepted, 2026-10-03 JST)

Close this small optimization gate. Keep `GGML_VK_GET_ROWS_128X4` default OFF
and retain the experimental implementation and evidence for reference. Do not
run normal ABBA, extend this candidate to 128k/256k, sweep thresholds or broaden
it into cache-layout/gather-matmul fusion work. The planned trigger for normal
ABBA (target gather and GPU-total improvement) was not met. Proceed to
VULKAN-002's missing grouped-union PP path, with long-context PP as its primary
goal. This decision closes the tested candidate, not every possible cached-pool
optimization.
