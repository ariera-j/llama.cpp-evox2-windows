# r5 MTP ON PP overhead — source review and investigation plan (2026-10-13)

**Status:** Investigation approved; this document is research/measurement design, not a validated PP fix. The stable r5 inference source and pinned upstream must remain unchanged. Experimental source instrumentation belongs on a separate branch. Reported PP is the **server slot prompt-wall timer**, not necessarily isolated `llama_context::t_p_eval_us`.

- Stable r5 upstream pin: `de7fa0a3c6a2e1b4cd9f22eb8d6bf5b12dbdb63b`. Do not move the r5 stable source.

Do not import DENSE/NOOP TG changes into the first PP experiment. This document is canonical on r5; experimental code remains branch-local.

## Key source-trace findings (pinned stable r5)

1. `tools/cli/cli.cpp`, `tools/cli/cli-context.cpp`, `tools/cli/cli-server.h`: current CLI launches a local server and uses its response/timing flow. Printed `prompt eval time` is generated by `tools/server/server-context.cpp::server_slot::print_timings()` using `server_slot_stats::t_prompt_ms()`, not the target's isolated `llama_perf_context::t_p_eval_us`.
2. `tools/server/server-common.h` ~393–470: `t_prompt_ms = (t_prompt_last − t_start) / 1000`; `server-context.cpp::metrics_post_decode()` advances `t_prompt_last` when prompt target batches complete, while `decode()` invokes `common_speculative_process()` **after** target `metrics_post_decode`. Subsequent prompt iterations therefore include between-batch MTP processing in reported wall time, but work after the final prompt timing update can cross the generation transition. Instrument boundaries before asserting exact additive decomposition.
3. `common/speculative.cpp::common_speculative_impl_draft_mtp` ~1428–1645: MTP constructor enables full target NextN output via `llama_set_embeddings_nextn(ctx_tgt,true,false)`. For non-shared Qwen4Exp, **every processed target batch** is paired with target hidden rows, then `llama_process(ctx_dft, LLAMA_PROCESS_TYPE_DECODE, batch)` fills the draft prefix; a `llama_get_embeddings_nextn()` read requires synchronization and `llama_get_embeddings_nextn_ith()` rows are copied into `verify_h`. `common_speculative_process` itself has no `t_draft_us` timer (that timer wraps only the `draft()` hook).
4. `src/llama-context.cpp` ~1642–1658, 4164–4173: NextN residual output uses `ggml_backend_tensor_get_async()` into a host buffer; accessing it calls `ctx->synchronize()`. Elapsed time around a getter can therefore include *preceding queued target GPU work* as well as actual transfer, **not** just memcpy. Enabling NextN extraction may also alter the target graph's output/selection path.
5. `src/models/qwen4exp.cpp::graph_mtp` ~548–637: ratio-zero MTP sidecar runs **dense attention**; the compatibility-only branch adds a ratio>0 guard around optional k-pool input creation. `src/llama-model.cpp` ~2695–2800: stable r5 creates hybrid indexer memory for Qwen4Exp MTP, explaining the separate DENSE TG patch, but its isolated DENSE/NOOP ABBA had little PP effect.
6. `tools/server/server-context.cpp::decode()` ~4167–4236 calls target decode, then speculative processing. Low-overhead timers should separate target work from draft MTP catch-up while respecting existing synchronization. GPU workload time and elapsed wall time are not interchangeable.

## Ranked hypotheses

| Priority | Mechanism | Why plausible | Distinguishing evidence |
| --- | --- | --- | --- |
| P0 | Full-length dense MTP draft prefill/catch-up at every target prompt batch | Verified `common_speculative_impl_draft_mtp::process` calls draft `llama_process` for each non-shared target batch; dense attention cost can scale with prefix length | Sum per-batch MTP process and draft-decode durations; depth/KV dependence |
| P0 | NextN hidden extraction: output materialization, sync, CPU-visible transfer, copy | ON enables unmasked NextN output; `ggml_backend_tensor_get_async()` and getter sync; 1024×10240 F32 output is ~40 MiB (historical width) | Getter/sync timings vs draft processing; host-copy GPU trace; batch-size dependence |
| P1 | Target graph/output path changes in MTP ON | `set_embeddings_nextn` changes output graph and buffers | Compare target graph, operators, copies, memory with NextN ON/OFF |
| P1 | GPU memory pressure/residency, draft KV growth, backend sync | r5 ON adds ~5 GiB to process GPU-local counters; backend deltas differ | UMA committed/shared/dedicated, GPU schedules and copy traces |
| P2 | CPU hybrid-indexer operations / speculative bookkeeping | DENSE/NOOP switches primarily improved TG, not PP | Investigate when P0 accounting leaves meaningful residual |

## Historical r2 MTP-QSA prototype: re-evaluation decision (2026-10-13)

**Decision: retain the r2 “no demonstrated PP benefit; do not port” verdict.** This applies to the *historical MTP-QSA implementation*, **not** to the new r5 PP bottleneck investigation. Keep `test/mtp-qsa-prototype` as a reference; do not cherry-pick it into the PP instrumentation branch.

The r2 prototype enabled draft-layer QSA where the Unsloth self-contained MTP sidecar reports compression ratio **0**, using a gated inferred reference ratio **4** for the known 48-trunk/one-NextN model topology. The first version ran a full-QSA path; the later design enabled it only for prompt-sized MTP batches with KV ≥ `LLAMA_MTP_QSA_MIN_KV=49152` and kept dense decode. It was **not** a general validated metadata conversion.

| Historical experiment | Context | MTP dense PP tok/s | MTP-QSA PP tok/s | QSA PP change |
| --- | ---: | ---: | ---: | ---: |
| r2 b10815 initial full-QSA | 64k | 259.23 | 259.12 | −0.04% |
| r2 b10816 revised prefill-only QSA | 64k | 255.73 | 252.97 | −1.08% |
| r2 b10816 revised prefill-only QSA | 128k | 209.44 | 207.93 | −0.72% |

These are **single pairs**, with variable generated lengths and acceptance, not repeatable ABBA confidence intervals. Historical *memo-only profiler* estimates draft-prefill FA ~5.35→4.42s (reduced by 0.93s), offset by indexer/top-k/gather/CONT overhead. Historical 128k memo-only draft compute buffer ~466.03→2736.05 MiB and GPU Local peak ~90.24→92.63 GiB (dense→QSA). These memory/operator values were **not independently reconstructed from the archived CSV and stderr**; do not present them as current measurements or proof of a particular operator's exact share.

Why the r2 trial is not a straightforward r5 patch:
- In pinned r5, `graph_mtp` shares `build_layer_attn()`, which has a **native conditional QSA/indexer path when the sidecar's per-layer ratio is positive and inputs exist**. Unlike the r2 experimental reference-ratio override, current Unsloth layer 48 ratio=0 takes dense attention. An inferred ratio=4 is a semantic/model-format intervention requiring quality/acceptance/correctness evidence, not merely a speed switch.
- r2's FA-only improvement did not overcome newly introduced indexing/gather operations or the overall MTP ON PP penalty. r5's QSA graph, k-pool implementation, synchronization and graph machinery have changed, so r2 per-op timings **cannot** be extrapolated quantitatively to r5.
- r2 short synthetic rollback/checkpoint smokes established only bounded functional smoke results, **not** bitwise hidden/logit identity or a general model-equivalence claim.
- Consequently **do not measure a copied r2 MTP-QSA port before phase profiling**. Only reopen a *new r5-native* sparse/draft-attention design if repeatable r5 64k/128k timing shows draft attention dominates the ON/OFF gap *and* the net indexer/gather overhead and model semantics can be addressed. Compare against the correct dense baseline, preserving target output, draft acceptance, and rollback evidence.

Original evidence: [r2 log recovery](R2-MTP-LOG-RECOVERY-2026-10-11.md), [r2 prototype code](https://github.com/ariera-j/llama.cpp-evox2-windows/tree/test/mtp-qsa-prototype), [r4 native-MTP review](R4-COMMON002-UPSTREAM-REVIEW-2026-10-04.md).

## Independent DeepSeek review triage — 2026-10-13 (incorporated with qualifications)

A user-supplied DeepSeek review was prepared from an **older repository snapshot**, before this plan and the completed r5 b11560 OFF/ON comparisons were indexed. Its recommendations were independently checked against the **pinned r5 Qwen4Exp graph** and prior r4 diagnostics. **Source of the proposals:** the user-provided 2026-10-13 DeepSeek Markdown review; the statuses below are our re-evaluation, not DeepSeek-validated tests.

### Descriptive r4 length scaling: useful as a profiler hypothesis, NOT an operator-time measurement

The older r4 ABBA series reports extra server prompt wall time at **61,789 / 126,253 / 255,181** input tokens: Vulkan **+14.58 / +45.44 / +155.99s** and ROCm **+10.92 / +30.44 / +94.14s** (from [r4 original controls](R4-COMMON002-OVERNIGHT-ANALYSIS-2026-10-04.md)). Fit the descriptive model `DeltaT = a + b x + c x²` with `x = N/61789`:

| Backend | fitted a (s) | b (s per x; approx us/token) | c (s per x²) | fitted quadratic share of DeltaT: 64k → 256k |
| --- | ---: | ---: | ---: | --- |
| Vulkan | +0.278 | 6.825 (~110.5 us/token) | 7.477 | 51.3% → 81.8% |
| ROCm | -0.075 | 7.219 (~116.8 us/token) | 3.776 | 34.6% → 68.4% |

**Three points exactly determine three parameters.** The “quadratic share” is only the algebraic share of this unconstrained fitting function; it is **not a measured draft-attention fraction**, nor do similar fitted b coefficients prove a CPU/host-transfer mechanism. Other prefix-dependent work (target QSA/k-pool, driver scheduling, allocator/UMA residency or per-ubatch sync) can also produce nonlinear depth trends. The r4 series differs in flags/builds from r5; do not fit these three r4 points together with r5 controls. Confirm attribution by **per-ubatch stage duration versus position/KV** (and GPU dispatch where justified), not by curve fit alone.

### Adopted cheap diagnostic gates, before any optimization

1. **Record each draft catch-up batch's input tokens, start/end positions, KV depth, and stage durations** (`llama_process(ctx_dft,...)`; target hidden getter/sync; batch setup/copy). Aggregate logs by coarse depth bins for the standard run, but optionally produce a *machine-readable, bounded per-ubatch summary* (no console spam). Plot draft elapsed time per token and per ubatch versus KV depth; normalize for varying batch size and observe transition around the last short batch. A rising trend is a **dense-attention hypothesis**, not its proof; measure actual FA/copy/operator time if it dominates.
2. **Check that draft context actually dispatches f16 Flash Attention**, rather than a non-FA fallback or unintended sparse/union path. Read `-fa auto`, draft KV f16 and native backend dispatch/graph shape. The **target** Vulkan union-activation banner does *not* identify **draft** attention. Current ratio-zero draft should take **dense attention**; dense attention can still be backed by Flash Attention. A scoped Vulkan FA counter or profiler trace is appropriate only if backend/source identity can be separated by target vs draft.
3. For cheap context evidence record **GPU Local / Dedicated / Shared, system committed and any available paging/budget metrics**, using the existing resource monitor. UMA/WDDM accounting is not proof of physical placement or GTT spill. Check whether a threshold/range change corresponds to measured delays; do not import a discrete-VRAM/GTT diagnosis from another AMD device.
4. Reuse the *design lessons*, **not the executable command**, from [r4 MTP diagnostics](R4-COMMON002-DIAGNOSTICS-IMPLEMENTATION-2026-10-04.md) and [r4 diagnostic run](R4-COMMON002-WALL-DIAGNOSTICS-2026-10-04.md): off/wall/sync separation, nested inclusive/exclusive timings, KV/dispatch metadata, native tests and completeness validation. Although the old `qwen38-r4-mtp-diagnostics.psd1` is carried in `tools/evox2/benchmark/configs/`, pinned r5 **does NOT contain `ggml/src/ggml-mtp-diag.h`** or the corresponding r4 source instrumentation. Setting `LLAMA_MTP_DIAG=wall` against the r5 compatibility-only binary will **not** magically produce `mtp-diagnostics.csv`. **Do not run the inherited r4 matrix as-is:** it targets `R4QsaUnionVulkan` and 128k/256k, with old flags and temperature 0.2. Add bounded r5-specific tracing and a 64k-first plan only after auditing the old source, adapting it selectively rather than bulk-porting it.

### Source-reviewed optimization candidates; gated and **not** implemented

| Candidate | Decision and priority | Required pre-implementation check |
| --- | --- | --- |
| **Draft KV-only / output-row-pruned prefill** (DeepSeek A1) | **Retain as high-upside HYPOTHESIS, not top implementation task.** Review after the draft-attention share is measured. | Pinned r5 `src/models/qwen4exp.cpp::graph_mtp` builds pre-attention per-token HC mix and all-token K/V, then `build_layer_attn`, HC combine, FFN and only **afterwards** `inp_out_ids`-selected `flat_out`; simply masking final output does **not** prune FA work. Test if *all earlier prompt tokens* need only draft KV, and whether **one/some required tail rows** need attention/FFN to continue drafting. Verify per-token Q/K/V are independent of same-layer output, that target NextN hidden input for **each** prompt token is still passed, that actual KV write/scheduler/cache paths are preserved, and that boundary h/logits, MTP acceptance and rollback match. Until these proofs, “O(N²) to O(N) with no quality impact” is **not established**. |
| **Target output-row / NextN pruning** (A2) | **Audit only, do not assume qwen4exp lacks it or that port is low-risk.** | r5 `graph::graph` already calls `crop_before_nextn(inp_out_ids)` near the last attention, and `crop_after_nextn` after constructing `t_h_nextn`. MTP ON explicitly requests **unmasked NextN output for every prompt token**, used by `common_speculative_impl_draft_mtp::process()`; naively cropping the target to its last row would **break the draft catch-up**. Measure which *post-NextN* output operations are still avoidable; separate this from reducing the mandatory target hidden rows. A qwen35-only upstream patch is not evidence of missing equivalent logic here. |
| **Device-resident target→draft hidden handoff** (B2) | **Conditional investigation after getter/sync share is measured.** | Estimate 10240×4 = 40 KiB per target token; 255181 tokens ≈9.73 GiB for a single full-width one-way payload, not proof of equivalent bus traffic or a >100 s bandwidth limit. Examine host wait/async-copy vs copy bytes and H2D draft input staging; same-UMA GPU memory does not automatically imply zero transfer/sync. Avoid blanket `ggml_backend_sched_synchronize` inserted for timing, which changes scheduler behavior. Half precision or projection fusion is a **separate numerics/model-semantics experiment**, not presumed safe. |
| **Target k-pool/layout CPU scans** (B3) | **Cheap counters only if residual remains; no automatic DENSE/NOOP re-port.** | r4/r5 DENSE and NOOP improve TG with negligible PP. Historical suffix rebuilds in generation are **not** proof that the same full scan repeats per PP ubatch. Count actual PP rebuild/copy/visited cells before revisiting. |
| **Reconvert MTP GGUF to ratio>0 QSA** (B4) | **Defer to independent correctness/model-provenance investigation.** | A GGUF metadata change is **not proof the checkpoint's head was trained for QSA**. r2 reference-ratio-4 prototype did **not** improve PP; require original trained attention definition, tensor presence, logits/acceptance and full model equivalence. Do **not** merely rewrite the existing ratio-zero sidecar or jump to 256k first. |
| **Backend FA optimization, KV quantization, larger ubatch, draft-max or delayed catch-up** (C/D) | **Defer until a stage-specific causal bottleneck is demonstrated.** | Larger ubatch can reduce launch/sync cost even if attention work remains, so it is a *controlled A/B hypothesis*, not categorically useless. Moving catch-up can shift time across the PP/TTFT boundary without improving end-to-end latency; count total request time. Any KV/precision change needs correctness/acceptance and normal unprofiled comparisons. |

### External issue/watch relevance (no direct Evo-X2 performance claim)

- [upstream issue #27428](https://github.com/ggml-org/llama.cpp/issues/27428): important as a target/draft timing and layer-split diagnosis example, **but its most severe ~2x PP reduction involves multi-GPU splitting**, whereas the current Evo-X2 run is one GPU; its causal explanation is not a measurement of r5 Qwen4Exp.
- [upstream issue #27572](https://github.com/ggml-org/llama.cpp/issues/27572): highlights asynchronous NextN output and HIP input-buffer ordering / concurrency concerns, but discussion contains **revised and contested diagnoses** (D2H vs H2D race). It is a correctness/synchronization caution, not evidence that extra synchronization will speed PP or that one specific race exists in this r5 run.
- [upstream issue #26432](https://github.com/ggml-org/llama.cpp/issues/26432): example of runtime memory pressure causing severe slowdown on a **discrete** ROCm device; only motivates checking actual Windows UMA budget/paging counters.
- Current benchmark policy remains **64k first, then 128k, ROCm cross-check, and optional 256k**. Do not revert to the older review's `upstream-watch` / clean-baseline-first interpretation: successful r5 b11560 MTP OFF/ON ABBA already exists and is the reference.

**Promotion gate:** no code optimization until the traced extra server PP time is split into target path, NextN copy/sync, draft input/graph/FA and residual, ideally explaining ~80% with honest boundaries. Afterwards test one isolated source idea, verify **unprofiled** PP and TTFT/end-to-end time, output/hidden/logit tolerances and acceptance/rollback, and repeat at 64k/128k; 256k only on evidence. Keep TG branches frozen.

## Staged experiment plan

**Stage 0 — freeze and audit (read-only):** Record precise runtime source SHA/exe+DLL hashes, AMD driver/UMA settings, GGUF paths+sizes, input SHA256s, environment and CLI flags from prior r5 ABBA. Confirm old tested b11560 binaries still exist; do not repeat good baselines unless metadata differs. Check Windows `local.psd1`, build manifests, and version outputs. No upstream refresh or stable inference-source changes.

**Stage 1 — normal 64k Vulkan reference:** On compatibility-only runtime, short MTP smoke then normal 64k ABBA OFF–ON–ON–OFF if baseline source/runtime identity changed; otherwise reuse 2026-10-11 ABBA as control. Match 61,789 tokens, `-c 65536 -b 2048 -ub 1024 -n 512`, draft max 2/min 0, f16 target+draft KV, `--temp 0 --seed 1234 --ignore-eos`, Vulkan union ON threshold 32768, `--cache-ram 0 --ctx-checkpoints 0t`, no perf logger/trace. Capture native PP+TG, elapsed process/first-token latency, resource CSV, acceptance, output hashes. MTP OFF/ON need not yield identical output.

**Stage 2 — opt-in, low-volume phase instrumentation (separate branch):** Fork **exact** compatibility-only source `f8d24494f`; leave stable untouched. Trace OFF must preserve normal timing. With trace ON print **one aggregated breakdown plus coarse KV/depth bins**, never per-ubatch console spam. Separate (a) target call/submission and effective synced completion; (b) `common_speculative_process` overall; (c) target NextN getter/sync; (d) draft batch preparation; (e) `llama_process(ctx_dft...)`; (f) verification hidden-row copying; (g) other bookkeeping. Record counts, tokens, KV range, phase total/max. Avoid double-counting and do not add forced GPU synchronization to ordinary trace. If true GPU kernel timing is needed, use a **distinct forced-sync/profiler cohort** and note the changed workload. Current PP timer boundary near the final prompt batch needs special accounting.

**Stage 3 — discriminate at 64k/128k:** Compare Vulkan trace OFF/ON at 64k, then 126,253 tokens with `-c 131072` once instrumentation overhead is acceptable. ROCm 64k confirmation precedes longer ROCm tracing. If draft attention dominates, test `-ub 512` vs `1024` A/B with **both MTP OFF and ON**; if target/hidden path dominates, inspect output/copy kernels and one bounded Vulkan RGP profile. Fix source/build/runtime identity for every comparison. Normal and profiler-enabled measurements are distinct cohorts.

**Stage 4 — stop and decide:** Stop when ~80% of the observed prompt-wall delta is consistently apportioned across two Vulkan depths, with ROCm sign consistency or a recorded reason for differences. Optimize **one mechanism at a time**, with isolated flag/source control and correctness (target logits/NextN hidden, draft acceptance, rollback and output). For ROCm, separately characterize same-setting nondeterminism; do not claim bitwise equivalence without evidence. Preserve all model/input/runtime/artifact and ZIP hashes. **256k OFF/ON remains optional** after memory/runtime review, not the starting experiment.

## Execution gates and branch safety

- **Do not** port r2 MTP-QSA, alter Vulkan union, refresh upstream, merge DENSE/NOOP, or optimize GPU kernels before phase attribution.
- Start tracing on the compatibility-only branch ancestry with **one ratio-zero guard only**, not on DENSE/NOOP code. Keep trace default OFF and run native/short correctness gates before real-input ABBA.
- The stable r5 branch holds documents and research decisions only. Source code and experimental scripts stay on investigation branches until later independently approved integration. Copy completed **report documents only** back to canonical r5 after each evidence milestone.
- Before measuring, confirm which source commit is **actually compiled**, not merely the branch/documentation HEAD. Keep b11560 and frozen DENSE/NOOP binary identities separate.
