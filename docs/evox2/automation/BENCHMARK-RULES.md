# EVO-X2 性能計測ルール

共通ルールと標準計測ツールの正本は GitHub の `main` に置く。計測の計画・実行前に本書と [AGENT-RULES.md](AGENT-RULES.md)、[実機環境](EVOX2-ENVIRONMENT.md)、[RUNBOOK.md](RUNBOOK.md)、[KNOWN-ISSUES.md](KNOWN-ISSUES.md) を確認する。実行承認、権限、GPU 異常時の停止条件は既存の運用文書に従う。ラッパーの引数や出力例は [ツール README](../../../tools/evox2/README.md)、過去の長文評価条件は [BENCHMARKING.md](../BENCHMARKING.md) を参照する。

## 1. 計測ツールの選択

運用者が従来の手動計測と同じ形式で確認できるよう、単一条件の `llama-bench` は `Measure-LlamaBench.ps1`、単一条件の `llama-cli` は `Measure-LlamaCli.ps1` を使う。条件・ビルド・モデル・run をまたぐ比較は原則 `Invoke-BenchmarkMatrix.ps1` から同じラッパーを呼ぶ。リソース監視は `Monitor-LlamaProcess.ps1` と既存の [ADLX GPU 監視ツール](../../../tools/evox2/adlx-gpu-monitor/README.md) を使う。

既存の出力形式を使い、未対応機能は既存スクリプトへの追加を優先して検討する。独自の計測ツールや形式は、演算単体テスト、特殊なプロファイリング、初期化診断などで既存ツールでは必要な情報が得られない場合に限り、理由、対象、変更された計測境界を記録する。Matrix が対象ブランチにない場合は、対応する既存ラッパーを使う例外と実行順を記録する。対象バイナリが実入力や明示 Context を受け付けるかを確認し、実入力の計測を目的とする際に bench が対応していなければ CLI を使う。

## 2. 計測前の確認と記録

| 項目 | 確認する内容 |
|---|---|
| ビルド | 製品ソースのブランチと SHA、ビルド番号、ビルドマニフェスト、EXE のパス・バージョン・SHA-256、必要に応じて DLL とツールチェーン。計測ツールの SHA も別に記録する。 |
| 実機 | バックエンド、ドライバ、GPU・デバイス選択、実機の UMA 容量、開始時と終了時の P-MODE。通常の性能比較は Performance を使い、別モードを使う場合は実験条件に明記する。取得条件と前回の計測条件を照合する。 |
| ワークロード | モデルのファイルと版・構成、入力ファイルと識別情報、実入力・合成入力の別、入力トークン数・生成トークン数、Context の指定値と実効値、batch、ubatch、threads、GPU offload、CPU MoE。 |
| 機能設定 | K/V それぞれの KV cache 形式、Flash Attention、MTP、warmup、prompt cache、必要に応じてチェックポイント・サンプラー、高速化フラグ、関連環境変数。 |
| 実行・監視環境 | 実行ユーザー、SSH・対話セッション等の種別、ADLX・カウンター・P-MODE の利用可否、競合する推論・ビルド・監視プロセス、計測開始前の物理メモリの使用量・空き容量、GPU メモリ、比較を左右するバックグラウンド負荷。 |

`conditions.json` などの自動記録を使い、実機で確認した UMA 条件をラッパーに渡す。ラッパーの条件記録にない確認事項や欠損は実験記録に補う。特に開始前のメモリと競合プロセスを確認する。識別情報やマニフェストの不一致は運用ルールに従って扱い、ファイル名だけからバックエンドや設定を判定しない。時刻、終了コード、収集先も保存する。

Windows の最終起動時刻と計測開始時の OS 稼働時間を記録する。標準の Measure は起動前に一度だけ取得し、`result.json` の `OsStartup`、`summary.csv`、Matrix の run 集計に記録する。取得失敗は出所・取得状態とともに残す。直前の正常シャットダウンが確認できない場合、OS 停止時間は欠損とする。OS の区間から物理電源 OFF 時間は決められない。 [取得仕様と SSH 検証](BENCHMARK-MATRIX-ROUNDS-B12651.md#os-稼働時間の追記と非推論検証)

## 3. Warmup と計測区間

- 定常的な PP/TG 比較では原則 warmup ON とし、比較構成間で揃える。過去データとの条件統一や固有の診断で OFF にする場合は目的と理由を記録する。実効条件は実行した EXE の対応引数と実際のコマンドから確認する。
- コールドスタート、モデルロード、コンテキスト生成、初回 eval、PP/TG、プロセス全体を別の区間として記録する。llama.cpp の版・経路によっては最初の eval 完了時に load time が更新されるため、ログの load time をモデルファイルの読み込みだけの時間として扱わない。各値に計測元と始点・終点を付け、異なるタイマーの差分を区間の実測値とみなさない。
- Perf Logger または RGP を使う診断は別 run として識別する。通常速度の比較は診断 Logger OFF の結果を使う。GPU カーネル累積時間、並行実行区間、PP/TG の wall time はそれぞれの定義で報告する。同時実行されるカーネルの時間の単純加算から経過時間を求めない。

## 4. 比較実験の設計

- パッチはできる限り独立に評価し、評価対象以外の条件を固定する。初期評価は各構成 3 run、微小差の確認は各 5 run 以上を目安とし、観測変動と実験目的に応じて回数とトークン数を決める。1 プロセス内の `llama-bench` repetitions と独立した起動回数を区別する。
- Base と変更版を交互に実行するか、ラウンドごとに順序を変える。比較ペア、ラウンド、予定順と実行順を保存する。複数条件は原則 Matrix で計画し、実行前に展開順と件数を確認する。 `Comparison` 設定は独立 run 数、ラウンド、基準構成と予定順を指定できる。 [ラウンド比較と統合検証](BENCHMARK-MATRIX-ROUNDS-B12651.md)
- 各 run の終了を確認し、必要に応じてクールダウンを設ける。前 run のメモリ解放を確認してから次に進む。固定の待ち時間だけで解放を判定しない。目的に見合った回数・規模を使い、不必要な長時間計測を避ける。

微小差の評価では可能な限り同じ OS 起動期間、同じ GUI・バックグラウンドアプリの状態を揃える。計測前にタスクマネージャを閉じ、起動期間が異なる比較や稼働アプリに差があった場合は結果に明記する。

## 5. 通常のリソース監視

通常の性能計測では原則、システム／プロセス監視と ADLX GPU 監視を両方有効にする。監視対象は以下のとおり。

- GPU 使用率、クロック、温度、電力、GPU メモリ使用量。アダプター全体と推論 PID の値を識別する。
- CPU 使用率、システムの物理メモリ使用量・空き容量、コミット量・上限。
- 推論プロセスの Working Set、Private Memory、Virtual Memory。
- ページ読み込みとページフォールト、ディスクの読み書き速度、バックグラウンドプロセスの負荷。
- P-MODE。開始・終了時の読み取りを使い、ADLX 電力からの推定を記録する場合は補助的な整合性情報とする。

当面は既存の通常監視間隔を使う。ラッパーの既定はリソース 2 秒、ADLX 2,000 ms、任意の詳細なバックグラウンド監視は 15 秒。記録された実際のサンプル間隔と件数を確認する。監視負荷を評価する場合は、専用の比較で監視あり・なしを区別する。

`evox2-runner` の SSH セッションでは ADLX、`Get-Counter`、一部 WMI の取得可否が異なる。プロセスの起動に加え、実際のサンプル件数、項目別欠損、警告を確認する。取得不能の値は欠損として扱い、現行 CSV の既定のゼロ埋めが疑われる場合は可用性フラグや生ログと照合する。未取得を実測ゼロに読み替えず、確認できる値を保存する。監視が不完全な run は制約を明記する。P-MODE は [承認済みの読み取り手順](PMODE-PROBE.md) に従う。監視のための権限変更や安全設定の緩和には既存の承認ルールを適用する。

| 用途 | 運用上の設定 |
|---|---|
| 通常の性能計測 | 通常監視 2 秒＋ADLX 2,000 ms |
| モデルロード・メモリ調査 | 通常監視＋ADLX＋RAM 詳細 250 ms |
| 短時間の RAM ピーク調査 | 通常監視＋ADLX＋RAM 詳細 100 ms |
| 微小な性能差の最終確認 | 必要に応じて周期監視なしの対照計測 |

`-ResourceMonitor` と `-RamDetail` は明示指定。通常監視は2秒、ADLXは2,000 ms、詳細監視は有効化した場合に250 msが引数の既定。ADLX はラッパーの通常の自動検出と `-NoAdlxMonitor` が使用できる。リポジトリ外の ADLX は `-AdlxMonitorExe` で指定できる。対照条件では `-ResourceMonitor` と `-RamDetail` を指定せず `-NoAdlxMonitor` を使い、同じラウンドの比較条件を記録する。

## 6. モデルロード時の詳細監視要件

過去の手動計測と IQ2_S 実験では、モデルロードまたは初回 eval 付近の異常低速が記録された。運用者はモデルロード時に RAM が一時的に増える場面を観測し、関連を疑っている。当該実験にはリソースログがなく、直接の原因は未特定。経緯とタイマー境界は [IQ2_S 実験記録](../iq2-s-vulkan-matvec-20261125/README.md#低速2件の生ログ再解析) を参照する。

今後の詳細計測では、プロセスの起動前から終了後のメモリ解放確認までシステム時系列を取り、PID の寿命内ではプロセス時系列も取る。物理 RAM のピーク使用量と最低空き容量、ピークの継続時間、Working Set・Private Memory・Virtual Memory、コミット量・上限・System Cache、ページ読み込み・ディスク I/O、GPU メモリ使用量を記録する。モデルロード、コンテキスト生成、初回 eval、PP/TG を共通時刻軸に対応付け、境界が不明な区間は明示する。

Measure 系に `-RamDetail` を指定して通常監視と独立した前後観測と軽量 RAM 収集を有効にできる。250 ms は実装上の初期値で、100 ms とともに非推論で検証した。通常計測は通常監視2秒と ADLX 2,000 ms を揃える。詳細診断は250 msから始め、短いメモリ変化を追う必要がある場合に100 msを選ぶ。b12676／IQ3 PLE16の3ラウンドでの精度と別条件への適用の限界は、[実モデル統合検証](BENCHMARK-MATRIX-ROUNDS-B12651.md#event-log-readers-追加後の再開)を参照する。詳細サンプラーはネイティブ API を使い、高頻度の `Get-Counter`・WMI は行わない。受信時刻と内部処理境界、回復判定の限界を明記する。 [作業 3-3 の実装・検証記録](BENCHMARK-RAM-DETAIL-B12651.md)

UMA では CPU 側物理 RAM と GPU 側の計数範囲が重なり得るため、それぞれの項目と取得元を確認し、単純に合算しない。

## 7. 異常値と結果の評価

全 run の生データを保存する。各値、中央値、最小値、最大値、同じラウンドの Base に対する差を確認する。異常値を無断で除外せず、除外の根拠と除外前後の結果を記録する。差が通常の変動幅に比べて小さい場合は採用を裏付ける高速化と判断しない。

ロード、初回 eval、定常 TG の異常を区別し、原因未特定の場合は観測事実と推定を分ける。GPU 時間はタイマー境界と重複の扱いを添えて報告する。正当性の検証結果と性能評価は別に記録し、検証済み・未検証の条件を示す。GPU 異常や実行失敗時は [AGENT-RULES.md](AGENT-RULES.md) と [KNOWN-ISSUES.md](KNOWN-ISSUES.md) の停止条件に従う。Matrix の継続オプションを使う場合も停止条件を優先する。

障害復旧後の無人計測は、各 run 終了時に SSH、結果 JSON、対象・監視プロセス終了、RAM／コミット／GPU メモリの回復、P-MODE、新規重大イベントを確認する。必要な確認ができない場合は開始または続行を停止する。SSH 切断後に実機側が次の run を開始できないよう、コントローラーから1件ずつ起動する方式を使える。evox2-runner の System／Application の読み取り方法と欠損の区別は [実機環境](EVOX2-ENVIRONMENT.md#ssh-のイベントログ読み取り) を参照。再試行は運用者の判断を待つ。 [M005 復旧時の停止記録](INCIDENT-20261126-M005.md#復旧確認再開条件)

## 8. 結果と再現情報の保存

従来のラッパーと Matrix の出力形式を優先する。Matrix plan・展開順・実行条件、実際のコマンドラインと関連環境変数、各 run の結果と比較用集計、stdout・stderr、リソースログ・ADLX ログ、ビルド識別情報、異常発生時刻と観測内容、評価と採否を対応付けて保存する。収集できなかったログは状況を記録する。

GitHub には確定した実験記録と再現に必要な成果物を保存する。大容量の生ログは実機の許可された保管先に保持し、実験記録から保管先・run ID・ファイル名を特定できるようにする。必要に応じてハッシュも残す。認証情報、Git 管理対象外のローカル設定、秘密を含む環境変数は公開リポジトリに含めない。再現用には公開可能な設定例と実際に使った条件の記録を保存する。

## 9. 現行の対応範囲と修正候補

main と現行製品ブランチは作業3-5で標準計測ツールを共有した。各作業の計測条件と検証の来歴は固定 SHA に基づく。 [統合と検証の記録](BENCHMARK-INTEGRATION.md)

| 機能 | 現在の動作 |
|---|---|
| Matrix | 旧 plan の対応を保持し、ABAB／ABBA／Rotate／Explicit、比較グループと Base、独立反復、欠損を保ったラウンド比較を提供する。`PlanOnly` は展開のみ。Measure の `DryRun` は EXE 識別とコマンドの確認まで。 |
| 通常監視・ADLX | `resources.csv` の既存列に状態とネイティブ情報を追加。ネイティブ RAM・PID メモリ・PerfMon は取得元ごとに保持し、実測0と欠損を区別する。監視品質は推論成否と別に記録する。 |
| RAM 詳細監視 | 起動前・実行中・終了後の時系列、使用量ピーク、回復、マーカー受信時刻を保存する。間隔や回復の意味は [作業3-3](BENCHMARK-RAM-DETAIL-B12651.md) を参照。 |
| OS 起動情報 | 起動前に一度だけ稼働時間、起動時刻、利用可能なシャットダウン情報を記録。取得失敗、異常終了、正常終了時の停止期間を区別する。 |

実モデル検証は [作業3-4](BENCHMARK-MATRIX-ROUNDS-B12651.md) に記録した。環境ごとの取得制約、フェーズマーカーの網羅性、回復判定の範囲は各 run で確認する。詳細監視の時刻を内部処理の厳密な境界に使う方法や、監視品質に応じた再計測基準は後続候補。
