**Times below are CPU-observed wall intervals, not GPU operator timing. Nested intervals must not be added twice.**

| ↳ ↳ `llama_get_embeddings_nextn(ctx_tgt)` target hidden getter | **78.439138 s** |
| ↳ ↳ draft batch preparation | **0.001212 s** |
| ↳ ↳ `llama_process(ctx_dft)` CPU call(s) | **6.756183 s** |

| Existing target explicit sync (subset of target wrapper) | **1.204144 s** |

The **78.439 s is mostly/possibly queued target GPU completion waited by the synchronizing getter**. It is *not* 78 s of pure data transfer overhead and not an independent addition to OFF target time. The target ON wrapper (`94.147s`) alone looks ~77s faster than OFF (`171.105s`) because async work may be completed within the ON getter; this must not be mistaken for a target speedup.

For **accounting only** (not operator-causal attribution), comparing disjoint ON intervals against OFF target wall gives:
- ON target wrapper + ON hidden getter − OFF target wrapper = **`(94.146544 + 78.439138 − 171.105467) = +1.480215 s`**. This residual includes any target graph/output/scheduling change and/or shifted GPU waits, **not a measured hidden-transfer cost**.
- ON-only draft `llama_process` CPU-call time = **+6.756183 s**; ON-only verify hidden getters and host copy = **+1.923453 s**; remaining stage bookkeeping, caller overhead/recording approximately **0.005s**.
- Combined observed trace penalty **`181.270576 − 171.105467 = +10.165109 s`**, consistent with server prompt **+10.187190 s**. Do not interpret draft `6.756s` as isolated FA GPU operator time; source may submit async work or block in later calls. This is a useful **accounting decomposition, not a proven causal decomposition**.

### Depth trend: supports investigation, but does not prove FA cost dominance

| Prompt range (end-position KV bins) | MTP OFF batch wall | MTP ON batch wall | ON−OFF | ON draft `llama_process` calls |
| --- | ---: | ---: | ---: | ---: |
| 0–32,768 | 80.395170 s | 88.622596 s | **+8.227426 s** | 2.942170 s |
| 32,769–61,789 | 90.710297 s | 92.647980 s | **+1.937683 s** | 3.814013 s |

Per-full-2048-token-batch draft `llama_process` wall rises almost linearly with depth: **~130 ms at KV4096 to ~310 ms at KV61440**, excluding first-batch initialization outlier (~192ms at KV2048) and the final 349-token batch (~27ms). Simple correlation across full batches #2–30: **Pearson r≈0.997**, approximate observed slope **3.01 ms per additional 1000 KV tokens** for this *CPU-call wall*, not evidence of a particular GPU kernel shape. Check actual draft f16 FA backend dispatch/profile before claiming “dense attention is the cause.”

The reported **ON−OFF wall penalty is larger in the first 32k (+8.23 s) than the next ~29k (+1.94 s)** even though the draft-call wall increases later. The Vulkan union threshold is 32768, but this alone does **not** establish union dispatch as the causal explanation; it highlights why fitting the total PP slowdown to a single draft N² term is unsafe. The last 349-token batch also differs in execution shape from full batches; analyze separately.

## Resource and system I/O observation (single run per arm)

64k reported sampled peaks:

| Counter | MTP OFF | MTP ON |
| --- | ---: | ---: |
| Process GPU Local | **80.614 GiB** | **85.572 GiB** |
| Process GPU Dedicated | **79.928 GiB** | **84.000 GiB** |
| Process GPU Shared | **0.686 GiB** | **1.572 GiB** |
| System committed | **91.634 GiB** | **98.036 GiB** |

During the overlapping post-load **50–190 seconds after process start** resource-sampling window (approximately 69 samples each), median system-wide `DiskRead_MiBps` **OFF ~0.03 vs ON ~14.6**, and median `PageReads_PerSec` **OFF 1 vs ON ~525** (median `PagesInput_PerSec` OFF 7 vs ON ~3749). This is a real correlation in these logs, **not demonstrated process-private paging or UMA residency failure**. Early huge disk reads are ordinary model loading and excluded from the quoted window; page counters include unrelated system activity. MTP ON also adds a distinct Q8_0 model and extra host-visible model buffers. Recheck whether the ongoing I/O appears in repeated normal 64k/128k ON runs, whether it correlates with PP pauses, and whether other system processes contribute before attributing slowdown to memory pressure.
