## Question, inputs and source pin

Investigate why r5 ROCm PP for real-text inputs has little corpus-dependent variation while Vulkan union OFF shows a strong Japanese-literature versus llama.cpp C/C++ source gap, and identify actual HIP FA source paths before instrumenting or porting any algorithm. Source is the stable [r5 branch](https://github.com/ariera-j/llama.cpp-evox2-windows/tree/r5/upstream-refresh-20261009), pinned upstream `de7fa0a3c6a2e1b4cd9f22eb8d6bf5b12dbdb63b`. Source readings were made after documentation commit `fd213fe6a5981c28a92dbb4ff89c8ed5f7d75528`; neither that commit nor this document modifies native FA code. Model for prior tests: Qwen3.8-Flash-Next Unsloth UD-IQ3_XXS PLE16, f16 KV, MTP OFF; Windows Evo-X2 Radeon 8060S / gfx1151, configured UMA 96 GB.

**Already measured (not a new source-investigation measurement):** [r5 real-corpus ROCm/Vulkan table](R5-ROCM-VULKAN-CORPUS-PP-64K-128K-2026-10-10.md) gives at 64k (61,789 tokens) ROCm Japanese literature **404.027**, code **394.669** tok/s; Vulkan union OFF literature **285.479**, code **329.465** tok/s; at 128k ROCm literature **301.542**, code **296.075** tok/s. Each ROCm corpus had one run and each backend had distinct binaries/conditions, so small rankings and cross-backend deltas do not identify a single kernel effect. Previous [Vulkan FA RGP/mask analysis](R5-VULKAN-OFF-FA-DISPATCH-DIAGNOSTICS-2026-10-10.md) established `KV=49152,N=1024` late-prefill `FA_MAIN` kernel time **~4.1× literature/code**, while complete skippable 16×64 mask-tile percentages were 35.68%/75.03%. That is **Vulkan-only evidence**.

## Source dispatch trace

1. [`ggml/src/ggml-hip/CMakeLists.txt`](https://github.com/ariera-j/llama.cpp-evox2-windows/blob/r5/upstream-refresh-20261009/ggml/src/ggml-hip/CMakeLists.txt) compiles the CUDA-shared `fattn` and template instances under `GGML_USE_HIP`. The host handles `GGML_OP_FLASH_ATTN_EXT` in [`ggml/src/ggml-cuda/ggml-cuda.cu#L2453-L2455`](https://github.com/ariera-j/llama.cpp-evox2-windows/blob/r5/upstream-refresh-20261009/ggml/src/ggml-cuda/ggml-cuda.cu#L2453-L2455), then [`fattn.cu#L540-L720`](https://github.com/ariera-j/llama.cpp-evox2-windows/blob/r5/upstream-refresh-20261009/ggml/src/ggml-cuda/fattn.cu#L540-L720) selects **VEC / TILE / MMA_F16** based on head dimensions, Q tokens, GQA/mask alignment and AMD WMMA/MFMA support; [`fattn.cu#L758-L776`](https://github.com/ariera-j/llama.cpp-evox2-windows/blob/r5/upstream-refresh-20261009/ggml/src/ggml-cuda/fattn.cu#L758-L776) launches the selected branch. This is **host-side eligibility**, not a captured runtime dispatch.
2. For `gfx1151`, [`common.cuh#L80-L92`](https://github.com/ariera-j/llama.cpp-evox2-windows/blob/r5/upstream-refresh-20261009/ggml/src/ggml-cuda/common.cuh#L80-L92) identifies RDNA3.5 and [`common.cuh#L356-L358`](https://github.com/ariera-j/llama.cpp-evox2-windows/blob/r5/upstream-refresh-20261009/ggml/src/ggml-cuda/common.cuh#L356-L358) makes `amd_wmma_available(cc)` true. With **head dimension 256, aligned f16 K/V, a usable QSA mask and a full 1024-token ubatch**, `Q->ne[1]*gqa_ratio_eff > 16` ordinarily meets [`fattn.cu#L699-L702`](https://github.com/ariera-j/llama.cpp-evox2-windows/blob/r5/upstream-refresh-20261009/ggml/src/ggml-cuda/fattn.cu#L699-L702), so **MMA_F16 / AMD WMMA is the most plausible 64k PP kernel**. A short tail ubatch, another attention layer, padding/alignment failure, or altered head/mask dimensions may take a different branch. Verify actual Q/K/V/mask shapes and captured dispatch before declaring the path proven.
3. The model's [`qwen4exp.cpp#L759-L889`](https://github.com/ariera-j/llama.cpp-evox2-windows/blob/r5/upstream-refresh-20261009/src/models/qwen4exp.cpp#L759-L889) generates pooled top-k cell IDs and materializes a **full-length, largely `-inf` sparse QSA mask**. [`qwen4exp.cpp#L892-L940`](https://github.com/ariera-j/llama.cpp-evox2-windows/blob/r5/upstream-refresh-20261009/src/models/qwen4exp.cpp#L892-L940) still passes **full K and V** to `build_attn_mha`, plus the selected-row hint. The r3 QSA budget `top_k=2048`, pool ratio 4 gave `n_sel≈2051`; confirm actual r5 metadata and mask visibility rather than assuming every cell is visible. The mask can be sparse throughout the KV history without making full K/V tensors small.
4. **CUDA-only compact sparse FA is disabled in HIP.** [`fattn.cu#L106-L151`](https://github.com/ariera-j/llama.cpp-evox2-windows/blob/r5/upstream-refresh-20261009/ggml/src/ggml-cuda/fattn.cu#L106-L151) aborts compact-mask generation on HIP, and `ggml_cuda_flash_attn_ext_mma_f16_shall_use_sparse` returns false. [`fattn-mma-f16.cuh#L2054-L2105`](https://github.com/ariera-j/llama.cpp-evox2-windows/blob/r5/upstream-refresh-20261009/ggml/src/ggml-cuda/fattn-mma-f16.cuh#L2054-L2105) excludes the sparse template under `GGML_USE_HIP` and invokes `launch_fattn(..., stream_k=true, use_sparse=false)` for MMA. **Do not enable sparse by deleting guards**: host compact-mask generation and kernel eligibility/types/semantics need independent design and correctness tests.
5. There **is** a different mask optimization: [`fattn-common.cuh#L1113-L1133`](https://github.com/ariera-j/llama.cpp-evox2-windows/blob/r5/upstream-refresh-20261009/ggml/src/ggml-cuda/fattn-common.cuh#L1113-L1133) uses `scan_mask = !use_sparse && mask && K->ne[1] % 256 == 0 && (Q->ne[1] >= 1024 || Q->ne[3] > 1)`. [`flash_attn_mask_to_KV_max` at #L669-L723](https://github.com/ariera-j/llama.cpp-evox2-windows/blob/r5/upstream-refresh-20261009/ggml/src/ggml-cuda/fattn-common.cuh#L669-L723) scans **backwards across 256-key blocks** until reaching the last block not fully masked and supplies a **suffix cutoff**; [`fattn-mma-f16.cuh#L1926-L1935`](https://github.com/ariera-j/llama.cpp-evox2-windows/blob/r5/upstream-refresh-20261009/ggml/src/ggml-cuda/fattn-mma-f16.cuh#L1926-L1935) limits the attention KV loop. For full 1024-token ubatches with padded K and a mask, this scan **can execute**. It is **not** the Vulkan interior-tile 2-bit classification/skip. QSA's recently visible tail may keep the rightmost live block near the end, making the suffix cutoff nearly ineffectual; **this is a hypothesis**, and the actual computed `KV_max` has not been observed.
6. [`fattn-common.cuh#L1145-L1220`](https://github.com/ariera-j/llama.cpp-evox2-windows/blob/r5/upstream-refresh-20261009/ggml/src/ggml-cuda/fattn-common.cuh#L1145-L1220) is the **MMA Stream-K scheduler**, not Vulkan Split-K. The MMA case passes `stream_k=true` to the launcher, but `should_use_stream_k` can select one whole output tile per group depending on tile count, occupancy and efficiency. On AMD WMMA, `DKQ==64` has a special affirmative branch; at `DKQ==256`, the regular efficiency criterion still decides. `stream_k=true` in the call **does not establish that splitting was actually selected**. The generic TILE kernel uses `stream_k=false`.
7. No equivalent to the measured Vulkan `16×64 ALL_NEG_INF` metadata skip was located in the traced HIP MMA path. Absence of that particular fast path **does not prove** no internal mask-related savings in every HIP FA kernel. Source inspection alone cannot quantify GPU bandwidth, latent operator bottlenecks or whole-run causality.

## Review of upstream HIP FA correctness fix #30103

[ggml-org/llama.cpp PR #30103](https://github.com/ggml-org/llama.cpp/pull/30103) merged **2026-10-10**, after the r5 upstream pin; the **one-line** change in [`fattn-mma-f16.cuh#L1775-L1777`](https://github.com/ariera-j/llama.cpp-evox2-windows/blob/r5/upstream-refresh-20261009/ggml/src/ggml-cuda/fattn-mma-f16.cuh#L1775-L1777) is:

```diff
-        if (np > 1) {
+        if (np > 1 || nbatch_combine != DKQ/2) {
             __syncthreads();
         }
```

**Important narrower applicability finding:** `nbatch_combine != DKQ/2` alone does *not* imply the existing r5 build missed synchronization. The fix changes execution only where `np == 1` and the combine batch differs. With the **RDNA `DKQ=DV=256` MMA `ncols=64`** configuration in [`fattn-mma-f16.cuh#L161-L164`](https://github.com/ariera-j/llama.cpp-evox2-windows/blob/r5/upstream-refresh-20261009/ggml/src/ggml-cuda/fattn-mma-f16.cuh#L161-L164), `nthreads=256`, hardware `warp_size=32`, `cols_per_warp=16`, so `nwarps=8`, `np=8×16/64=2`. For `ncols=32`, `np=4`. In **those particular 256-head-size configurations**, r5's existing `if (np > 1)` already synchronizes, despite the **ncols 32/64** `nbatch_combine=64` versus `DKQ/2=128` difference. This reduces the urgency of #30103 **for these specific PP configs**; it does **not** prove the fix is irrelevant to other dimensions/kernel variants or that no race exists. It is not an observed output bug on Evo-X2. Preserve the upstream correctness-fix candidate and test it separately only if its selected runtime shape meets the newly covered predicate or relevant correctness work is undertaken.

## Tool feasibility, planned low-cost runtime gate

- AMD documents **Radeon GPU Profiler for Windows HIP** in [RGP supported compute APIs](https://gpuopen.com/rgp/) and [Windows HIP SDK component support](https://rocm.docs.amd.com/projects/install-on-windows/en/latest/conceptual/component-support.html). More importantly, this project previously captured **ROCm/HIP RGP dispatch timer traces** on this Evo-X2 in [ROCM-QSA-PROFILING-SOURCE-TRACE-2026-10-01.md](ROCM-QSA-PROFILING-SOURCE-TRACE-2026-10-01.md): r3 steady decode `flash_attn_tile<256,256,1,4,false>` ~1.452 ms (128k) and ~2.939 ms (256k). RGP feasibility for this **r5 binary/toolchain and long PP capture** must still be checked; do not claim a successful r5 profile.
- **First gate (no source edits):** use the already documented 64k **Japanese literature and llama.cpp code** inputs, pinned r5 ROCm build b11543 / binary SHA256 `fc6559c7cc6f07063fe4c44ab94f29a380598d26b3902bc0c90ba99847b8872c`, f16 KV, MTP OFF, `-c 65536 -p 61789 -b 2048 -ub 1024`, same model/path and input hashes in [benchmark report](R5-ROCM-VULKAN-CORPUS-PP-64K-128K-2026-10-10.md). Before collecting long runs, smoke-test the RGP HIP application capture/dispatch view on a short workload. Use the existing real-input benchmark wrapper or the same known-valid `llama-bench` command that produced the archived results.
- If capture works, identify at a comparable **KV≈49152, Q=1024** FA node: actual template/kernels, `scan_mask` kernel presence, FA MMA/TILE choice, any Stream-K fixup, and FA kernel duration. Separate scan, main FA and fixup times, then estimate FA vs other operator share; capture at least one matching node per input rather than assuming Vulkan node names and HIP names coincide. RGP capture overhead/trigger windows are a known practical limitation.
- **Stop rule:** if the selected HIP path and its FA contribution are clear, decide whether remaining ROCm 128→256k PP scaling deserves an investigation or whether to move to **COMMON-005 ROCm decode**. If FA is not materially dominant, do not begin a wholesale HIP sparse-prefill port. Do **not** start a new optimization patch solely from the source-level absence of Vulkan's interior skip.
- If #30103 is tested on a future branch, preserve r5 baseline and execute focused HIP `test-backend-ops` FA correctness/greedy gates. The change must be an isolated cherry-pick/patch with its own source and binary identity; no performance win is inferred from correctness synchronization.
